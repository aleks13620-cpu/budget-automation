# Worker-бриф — Замечания оператора: видимость тегов + кнопка «вопрос» + авто-уведомление

> Отдельная задача (паттерн оркестратор+worker, по правилам проекта). НЕ строить в чате-обсуждении.
> Цель: оператор фиксирует вопрос/проблему в системе в один клик → команда видит сразу (без звонков),
> НЕ нарушая правило «данные хранятся на российских серверах».
> Создан 2026-06-01 после деплоя #4 (bc03dcc), по запросу владельца.

## Контракт (зачем)
Замечания оператора — сигнал, который делает систему точнее (ядро продукта: обучение через подтверждения + ранняя ловля парс/матч-проблем). Сегодня сигнал теряется: связь идёт по телефону, системная форма замечаний недоиспользована (память: 1 запись на 6 устных проблем). Довести до «оператор кликнул → команда получила уведомление».

## Текущее состояние (проверено в коде 2026-06-01)
- Таблица `operator_feedback`: `type, project_id, supplier_id, spec_item_id, invoice_item_id, comment, status, created_at` (`schema.ts:223`, миграции `init.ts:53+`).
- Ввод оператора УЖЕ есть:
  - **7 one-click тегов** — `POST /api/projects/:id/feedback/tag`, safelist `ALLOWED_TAGS` (`matching.ts:1995`): `price_wrong, wrong_marking, needs_alternatives, duplicate, not_purchased, analog_brand, parser_missed`. Пишется строкой `type='tag_<name>'`.
  - **Свободный текст** — `POST /api/projects/:id/feedback` (`matching.ts:1970`), `type='error_report'`.
- Вывод УЖЕ есть: `GET /api/feedback/all` (`:2033`), `GET /api/feedback/export` xlsx (`:2060`), `PATCH /api/feedback/:id/resolve` (`:2021`).
- **ДЫРА 1:** `/feedback/all` и `/feedback/export` фильтруют `type='error_report'` → **теги (`type='tag_%'`) НЕ видны** в списке/выгрузке. Самый лёгкий ввод невидим на выходе (вероятная причина «никто не пишет»).
- **ДЫРА 2:** нет тега «вопрос / не уверен» — только конкретные проблемы.
- **ДЫРА 3:** нет push-уведомления — только pull (зайти в систему).

## Scope (3 части)
**Часть 1 — видимость захвата (мелко, низкий риск):**
- Включить теги (`type LIKE 'tag_%'`) в `/feedback/all` и `/feedback/export` с читаемыми RU-ярлыками. Мапа `tag→label` — ЕДИНЫЙ источник рядом с `ALLOWED_TAGS` (no-hardcode-в-разнобой).
- Добавить тег `question` («❓ вопрос / не уверен») в `ALLOWED_TAGS` + кнопку на review-экране фронта.

**Часть 2 — инбокс «Замечания» + механизм разбора (полный контент на RF-сервере):**
- Экран/виджет «Замечания»: список с фильтром по статусу + **счётчик НОВЫХ** (бейдж = «есть нерешённые вопросы»). Полные детали — здесь, на сервере. Сначала проверить, не покрыто ли уже UI поверх `/feedback/all`.
- **Статус:** Новое → Разобрано (`PATCH /api/feedback/:id/resolve` уже есть). Разбор = пройти по новым, по каждому: решить → «Разобрано», ИЛИ эскалировать.
- **Эскалация в план:** пометить замечание «→ задача» со ссылкой на запись реестра проблем (PRB). Это связь «папка замечаний → план проекта»: мелочь закрывается на месте, повторяющееся уходит в работу с обраткой-ссылкой.

**Часть 3 — авто-уведомление (push), residency-safe:**
- При новом замечании — отправка уведомления.
- **КОНТЕНТ-ПОЛИТИКА (residency, критично):** наружу уходит МИНИМУМ — проект, № позиции, ярлык тега, ссылка в инбокс. **БЕЗ названий материалов/поставщиков** (правило «данные не за рубежом» из пресс-релиза). Полный контент — только в системе.
- Канал — по решению владельца (см. таблицу). Рекомендация: Telegram-бот в рабочую группу.
- Конфиг: токен/chat_id из `.env` (НЕ в коде). **Секреты НЕ логировать.**
- Каденс: предпочесть дайджест («N новых по проекту X»), а не сообщение на каждый клик (анти-спам).

**Часть 4 — прикрепление скриншота к замечанию (по запросу владельца; КАНДИДАТ НА ОТДЕЛЬНУЮ ФАЗУ — больше работы):**
- Оператор может приложить картинку к замечанию. Инфраструктура загрузки файлов уже есть (multer, как у счетов/смет) — хранить файл, связать с записью `operator_feedback`, показать в инбоксе.
- **Residency:** скриншот хранится В СИСТЕМЕ; в Telegram НЕ отправляется (на картинке могут быть цены/названия = бизнес-данные). Пинг лишь сообщает «прикреплён скрин → смотри по ссылке».
- Из-за объёма (хранилище + UI загрузки + показ + валидация типа/размера файла) — рекомендую вынести в отдельную фазу ПОСЛЕ Ч1–Ч3, чтобы базовый цикл «клик → видно → уведомление» поехал быстро.

## Investigation-first (ДО сборки Части 3 — СТОП, вернуть оркестратору на «ок»)
1. ✅ **Доступность Telegram API — ПРОВЕРЕНО 2026-06-01 (PASS):** `curl https://api.telegram.org/bot0:0/getMe` с прод-сервера (Timeweb, RF) вернул `{"ok":false,"error_code":401}` = Telegram **достижим**. Канал зафиксирован = Telegram-бот в рабочую группу. Fallback (РФ-SMTP/инбокс) — только если связь когда-нибудь отвалится.
2. **Контент-политика:** подтвердить с владельцем «только ID + ссылка, без бизнес-текста».
3. **Каденс:** per-event vs дайджест vs «вопрос/срочное сразу» — предложить дизайн, ждать «ок».

## Критерии приёмки
- Теги видны в списке/выгрузке с понятными ярлыками; тег «вопрос» работает end-to-end (клик → запись → виден → уведомление).
- Новое замечание → уведомление (или, при недоступности TG, in-app бейдж/email) с **нулём бизнес-контента наружу**.
- Не ломает обучение/матчинг/существующий feedback (теги по-прежнему не попадают в обучающий сигнал как ошибки); `cd backend && npm run build` чистый; 5-move гейт PASS.
- No-hardcode (теги+ярлыки — единый источник; токен/chat_id в `.env`). Секреты не в логах.

## Процесс / правила
- Worktree от текущего `main`; forward-only (НЕ reparse); именованные файлы (НЕ `-A`/`.`; package-lock не коммитить).
- pre-deploy-check 5-move PASS перед `git push origin main`. **Move 5 особо:** утечка токена в логах, `.env` не в коммите, исходящие данные = соответствие residency.
- Деплой-верификация: SHA + CREATED-время контейнера + health; CREATED старое → ручной `docker compose up -d --build`.
- Память (читать): `reflection_2026-05-27_feedback_ux_gap` (недоиспользование, не доверять как полному сигналу), `reflection_2026-05-29_package_b_deployed` (#17 теги + safelist + валидация тегов на бэке, не на фронте), `reflection_2026-05-30_deploy_verification_gap` (push≠deployed), `reflection_2026-05-31_orchestrator_worker_pattern` (unit-green≠wired-in; серийные субагенты).

## Оценка
Сложность — **низкая**: захват почти готов (Часть 1 — мелочь), Часть 3 — тонкий слой отправки + investigation. Эффективность — **высокая при условии адаптации привычки** (оператор кликает, а не звонит); код убирает трение, привычка — главный рычаг.
