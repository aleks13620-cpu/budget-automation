## 2. Дефект (ДОКАЗАН сравнением: PDF-эталон через fitz ↔ прод-парс через API)
1. **КРИТИЧНО — потеряны ВСЕ количества.** `quantity = null` у **510 из 510 (100%)**. Значение из колонки «Количество» PDF попало в поле «номер позиции» (`position_number` числовой = 392 из 510). Доказательные пары PDF→прод: «Этажный узел на 4 квартиры» кол-во **3** → pos="3", q=null · «Теплосчётчик поквартирный» кол-во **132** → pos="132", q=null · «Радиатор Compact» кол-во **31** → pos="31", q=null.
   - Гипотеза причины: колонка «Поз.» в этом документе ПУСТАЯ почти во всех строках → ИИ, ожидая число в «номере позиции», взял туда количество и сдвинул соответствие колонок.
2. **Разрыв многострочных ячеек.** Одна позиция дробится на несколько. Пример (хвост): «Огнезащитная изоляция» / «EI 150» / «S=16мм» = одна позиция, разбита на 3. Следствие: 510 включает фрагменты, реальное число позиций меньше.

## 3. Почему важно (стратегически)
- Без количеств смету нельзя посчитать и корректно сопоставить → проект 12 как точка замера переноса ЗАБЛОКИРОВАН, пока не починим ЧТЕНИЕ.
- Это баг класса «коррупция на чтении» (родня ИТЕСА shadow-glyphs / НДС-сдвиг / Ровен form-B). Нарушает правило `no_corrupt_through`: сейчас 100%-битые данные текут в матчер/обучение.
- PDF структурно ЧИСТЫЙ (fitz отдаёт колонки идеально) → детерминированное извлечение таблицы по координатам колонок почти наверняка вернёт количества. Это направление фикса. Фикс хардит ЧТЕНИЕ для всех будущих загрузок со пустой «Поз.», не только проект 12 → кросс-проектная ценность.
