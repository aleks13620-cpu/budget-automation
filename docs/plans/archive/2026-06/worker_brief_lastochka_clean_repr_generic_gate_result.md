## Правила G1 / G2 (что именно обобщаем)
**G1 — вычитание атрибут-маркеров** (продукт/поставщик-агностично, применяется РАВНОМЕРНО ко всем 150, на не-вариантных = no-op). Паттерны (синтаксис атрибута, НЕ литерал товара):
```
/(?:^|\s)[А-Яа-яЁё]+(?:ое|ее)\s+исполнени\S*/gi          // "Левое исполнение." / "Правое исполнение"
/(?:^|\s)[А-Яа-яЁё]+(?:ое|ее)\s+подключени[ея][^\S]?/gi   // "Нижнее подключение", "Боковое подключение"
/(?:^|\s)d\s*п\s*=\s*\d+\s*мм/gi                          // "dп=15 мм" (диаметр ПОДКЛЮЧЕНИЯ, не DN товара)
/(?:^|\s)Q\s*=\s*[\d.,]+\s*(?:[ВвWw]т?\.?)?/gi            // "Q=2430 Вт"
/(?:^|\s)\d+(?:\s*,\s*\d+)*\s*этаж(?:и|а|ей)?(?=\s|$)/gi  // "2 этаж", "6, 7, 8, 9 этажи"
/\s\d+\s*Вт\.?\s*$/i                                      // хвост "1222 Вт"
```
Снятое → characteristics; остаток → ключ матча. Сознательно НЕ трогает голый DN/Ду/Дн/Ø (на трубах/опорах это различитель товара → no-corrupt-through).

**G2 — структурный родитель**: где у spec-позиции есть `parent_item_id`, ключ = имя РОДИТЕЛЯ, child-токены → characteristics.

## 5. ЧЕСТНЫЕ ГРАНИЦЫ ЗАМЕРА
1. **Суррогат остаётся суррогатом извлечения.** Я НЕ парсил исходный EVRA-PDF пр.11 (его нет локально; кэш-PDF — другой документ Royal Thermo с 0 EVRA). G1 применён к РЕАЛЬНЫМ прод-токенам full_name (извлечение зафиксировано) — измеряется ТОЛЬКО переменная «композиция/чистота ключа», как и anchored-суррогат. Реальный обобщённый парсер должен воспроизвести это вычитание на этапе парсинга (full_name=чистый продукт, маркеры→characteristics). Это UPPER BOUND чистки, не сквозная гарантия.
2. **Размер-вариант неоднозначность (B, 24 кейса).** rawSim не различает `CV33-200-1000` от `CV33-600-1000` (различие — цифры в хвосте, тонущие в строке). Матчер ставит верный в top-3..8, но не #1. Это структурная дыра матчера/типоразмеров, НЕ парсера — очистка ключа её не закрывает (и G1 её честно не приписывает себе).
3. **Операторская нестрогость Лев/Прав.** Часть 95-класса — исполнение лев/прав; в счетах оно то есть (`Лев`/`Прав` в скобках), то нет. G1 снимает «исполнение» из ключа → теряет этот различитель, но на confirmed-парах оператор связал по продукту (цена), поэтому потеря Лев/Прав не штрафуется в этом замере. В проде, если два зеркальных исполнения по одной цене — возможна неоднозначность лев↔прав (не ловится текущим эталоном).
4. **G2 не протестирован по существу** (0 пересечений parented-spec с confirmed-парами на пр.11). Вопрос «матчить на родителе» здесь не разрешён эмпирически — отложен; на пр.11 FK-родитель просто не дотянулся до нужного класса. G1 (текстовый) даёт тот же эффект без зависимости от FK.
5. **Сокольи baseline=0%** → «не упало» — слабая планка; ценность прогона = over-strip-тривайр (G1 не калечит чужой домен), не прирост.
6. **Эталонный пул пр.11 = 279 живых строк счетов** (idealized: верный аналог гарантированно в пуле для confirmed-пар). Реальная прод-выдача — больше пул/больше дистракторов; размер-вариант (B) там может быть хуже.

**Что GO означает конкретно:** реализовать в парсере спецификации обобщённое вычитание атрибут-маркеров (лексикон G1 как стартовый, расширяемый) так, чтобы `full_name`=чистый продукт, а снятые маркеры (исполнение/подключение/мощность/этаж) уходили в `characteristics`. matcher.ts НЕ трогать. Гейт качества парсера — `no_corrupt_through` (не опустошать строку: G1-guard оставляет оригинал, если вычитание убирает всё).

**Чего GO НЕ решает (для оркестратора/владельца):** size-variant (B, 24 кейса — крупнейший остаток, нужен размер-aware матч/LLM, отдельная цель ПОСЛЕ парсера) и coverage не-95 класса (D, 26 — трубы/изоляция, нужен каталог-KB, приоритет 3 параллельно). Парсер «чистого представления» необходим и переносим, но НЕ достаточен — он снимает один конкретный (доминирующий на ОВ-проектах) класс шума.

**Развилка G1 vs G2:** строить G1 (текстовое вычитание) — он переносим и доказан. G2 (FK-родитель) на пр.11 инертен (0 пересечений) — не строить как основной путь; родитель-линкинг полезен ортогонально (иерархия), но КЛЮЧ матча должен чиститься вычитанием, не браться из FK-родителя.
