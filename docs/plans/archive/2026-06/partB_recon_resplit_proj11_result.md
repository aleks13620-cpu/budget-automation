## ВЕРДИКТ: **GO** — путём **in-place UPDATE BY id** (НЕ `/reparse`, НЕ re-upload)

Доказанный CASCADE-safe рецепт: применить прод-трансформ `applyVariantMarkersToItems` к УЖЕ СОХРАНЁННЫМ `{name, full_name, characteristics}` строк пр.11 и `UPDATE … WHERE id=?` только изменённых строк, в одной транзакции, со снимком в `specification_items_history` до правки. Никакого DELETE/реинсерта → id стабильны → все связки (150 подтв. + ручные + жалобы-фидбек) целы. Прирост durable@1 пр.11 **4.7% → 55.3%** (≥ цель ~53%), **0 регрессий рангов**.

**NO-GO** на два альтернативных пути (оба рвут связки):
- ❌ **re-upload PDF** — CASCADE-DELETE 150 матчей + обнуление фидбек-связок + попадание в stale PDF-кэш (нужен был бы бамп версии).
- ❌ **HTTP `/reparse`** — (а) DELETE+реинсерт рвёт матчи каскадом, **и** (б) у пр.11 НЕТ `raw_data` → эндпоинт вернёт 400.

## МЕТРИКА 1 — путь активации определён (код-цитаты)

### `/reparse` (`backend/src/routes/specifications.ts:478-532`) — НЕПРИГОДЕН по трём причинам

1. **Чистку ключа он бы делал** (вопреки опасению — проверено кодом): `parseFromRawData` (`excelParser.ts:544`@87dd821) → `linkDnChildren(processed)` (`:608`), а `applyVariantMarkersToItems(items)` — **последний оператор ВНУТРИ `linkDnChildren`** (`excelParser.ts:448-450`@87dd821, явный коммент «CHOKEPOINT (Excel path)»). Оба входа парсера (`parseExcelFile` `:539` и `parseFromRawData` `:608`) зовут этот общий хелпер → маркеры вычитаются в любом пути. ✔ (это подтверждает [[reflection_2026-06-10_predeploy_gate_spec_clean_repr]] факт #1 в части «чистит ключ».)
2. **НО он CASCADE-UNSAFE:** `specifications.ts:503` `DELETE FROM specification_items WHERE specification_id=?`, затем реинсерт с НОВЫМИ autoincrement-id (`:512`). А `matched_items.specification_item_id → specification_items(id) ON DELETE CASCADE` (`schema.ts:107`, `init.ts:127`) при `PRAGMA foreign_keys = ON` (`connection.ts:18`) → **все матчи пр.11 удалятся каскадом**. Плюс `operator_feedback.spec_item_id … ON DELETE SET NULL` (`schema.ts:228`) → связки жалоб обнулятся.
3. **И он НЕДОСТУПЕН для пр.11:** read-only проба прод-снимка БД → у обеих спек пр.11 (id 5 «Отопление», id 6 «Вентиляция») `raw_data = NULL`. `specifications.ts:484` `if (!spec.raw_data) return 400`. Пр.11 — PDF-источник; `raw_data` сохраняется только для Excel-пути.

**Поправка к памяти:** [[reflection_2026-06-10_predeploy_gate_spec_clean_repr]] факт #1 («re-split через `/reparse` активирует чистку БЕЗ re-upload») верен ТОЛЬКО для спек с `raw_data` и БЕЗ операторских матчей. Для пр.11 (есть матчи + нет `raw_data`) `/reparse` **рвёт связки и недоступен**. Вектор «re-split БЕЗ re-upload» из мастер-плана реализуется **in-place UPDATE**, а не HTTP-`/reparse`.

### In-place UPDATE BY id (ВЫБРАННЫЙ путь) — CASCADE-safe

Читает каждую строку пр.11 → прод-трансформ `applyVariantMarkersToItems` (тот же, что в чокпоинте; идентичен проду) → `UPDATE specification_items SET name=?, full_name=?, characteristics=? WHERE id=?` ТОЛЬКО изменённых строк. Без DELETE/реинсерта → **id стабильны** → `matched_items`, `parent_item_id` (self-FK по id), `operator_feedback.spec_item_id`, `specification_items_history` — все целы.

## МЕТРИКА 2 — сохранность связок (offline, temp-БД из прод-снимка)

Свежий прогон `resplit-existing-proj11.mjs` (temp-БД в `os.tmpdir`, hard-guard против записи в прод):

```
seeded: 328 spec rows (proj 11), 150 confirmed matches (38 marked manual), 150 history
BEFORE: {spec:328, matched:150, confirmed:150, manual:38, history:150, orphans:0}
RE-SPLIT pass 1: touched=128  bareOrphanKept=72
AFTER : {spec:328, matched:150, confirmed:150, manual:38, history:150, orphans:0}
RE-SPLIT pass 2 (idempotency): touched=0
8/8 CHECKS PASSED — re-split is CASCADE-safe and idempotent.
```

- **id-сет стабилен**, matched/confirmed/manual/history **без изменений**, **orphans = 0**, **идемпотентно** (2-й проход = 0).
- Пример строки id=2953 (= живая жалоба **#433** «Левое исполнение. Боковое подключение dп=15 мм»):
  - `full_name` → **чистый** `"Радиатор настенный EVRA Compact C33-400-700"` (ключ матча),
  - маркеры → `characteristics` `"…; Левое исполнение.; Боковое подключение; dп=15 мм; Q=1222 Вт"`.
- **Оговорка о честности чисел:** демо моделирует ручные как 25% (=38), а НЕ брифовые 86. Механизм сохраняет ВСЕ `matched_items` независимо от `source`/количества (FK по id, id неизменен) → доказательство count-независимо. Точные ЖИВЫЕ счётчики (бриф: 150 подтв. + 86 ручных) сверить read-only GET НА ШАГЕ 2 (pre-flight, ниже) и проверить post==pre.
- **Стейл-предупреждение:** локальный `database/budget_automation.db` устарел (Jun 7: всего 6 матчей, 417 строк). Авторитет = кэш `Jun 10` (150 пар, 328 объектов) и ЖИВОЙ прод. Локальный `.db` НЕ основа сим (сим берёт кэш).

## РЕЦЕПТ ИСПОЛНЕНИЯ (гейтуемый, для шага 2 — оркестратор + владелец)

**Ограничение среды:** SSH/exec в прод-контейнер недоступны (память: «верификация через HTTP API»). Поэтому исполнение — через задеплоенный код + API (Опция A), либо in-container скрипт, если появится exec (Опция B).

### Опция A (РЕКОМЕНДУЮ): гейтованный server-side in-place re-split, by-id
1. **Новый код (через pre-deploy-check + build-before-push):** маленький, проектно-ограниченный, идемпотентный эндпоинт, напр. `POST /api/specifications/:id/resplit-clean` (или `…/projects/11/resplit-clean`), который для спеки делает **в одной транзакции**:
   - `saveSpecSnapshot(specId, 'resplit_clean_repr', db)` — существующий хелпер `specifications.ts:562` (снимок в history до правки);
   - `SELECT id, name, full_name, characteristics …` → `applyVariantMarkersToItems(rows)` → `UPDATE … WHERE id=?` только изменённых.
   - Гард: ограничить spec id перечнем пр.11 (5, 6) или проверкой `project_id=11`; не принимать произвольные id.
2. **Pre-flight (read-only, ЖИВОЙ прод, до правки):** зафиксировать для пр.11 `COUNT matched_items` total/confirmed/`source='manual'` + список `spec_item_id` жалоб (#433/#326/#472-478).
3. **Исполнение:** вызвать эндпоинт для spec 5 и spec 6 (по очереди).
4. **Post-gate (read-only):** assert matched/confirmed/manual **== pre**, orphans=0, фидбек-связки не NULL; затем **пере-прогнать матчинг пр.11** (подтверждённые остаются подтверждёнными; прирост ложится на текущие НЕ-сматченные/неверно-маркированные строки, вкл. жалобы).

### Опция B (если будет exec в контейнер): in-place скрипт внутри контейнера
Тот же трансформ + by-id UPDATE + `saveSpecSnapshot`, после файлового бэкапа БД. Нового эндпоинта не нужно, но требует exec-доступа, которого сейчас нет. Форма — `resplit-existing-proj11.mjs`, перенацеленная на прод-БД (НЕ temp), с теми же ассертами (id-сет стабилен, orphans=0).

## СВОДКА ВЛАДЕЛЬЦУ (простым языком)

Жалобы по радиаторам Ласточки (#433/#326/#472-478) держатся, потому что у УЖЕ загруженных строк пр.11 «грязный» ключ матча (внутри имени сидит мусор вроде «левое исполнение, dп=15 мм, Q=1222 Вт»). Форвард-фикс чинит только НОВЫЕ загрузки. Перезалить файл нельзя — это сотрёт 150 подтверждённых совпадений и ручные связки (каскадное удаление по базе). Кнопка «пересобрать» (`/reparse`) тоже не годится: она пересоздаёт строки (те же связки слетят) и вдобавок у Ласточки не сохранён «сырой» PDF-текст, нужный этой кнопке.

**Безопасный способ найден и доказан числами (офлайн, прод не тронут):** аккуратно «почистить» текст прямо в существующих строках по их id — связки при этом НЕ трогаются. Проверка: 0 потерянных связок, повтор безопасен (ничего не портит), а точность матчинга на чистых ключах прыгает с **4.7% до 55.3%** при **нуле ухудшений**. Версию парсера бампать не надо.

**→ Нести оркестратору Арте на гейт исполнения (шаг 2).** Исполнение = задеплоить маленький проектно-ограниченный эндпоинт «почистить пр.11» (через pre-deploy-check), снять счётчики связок ДО, вызвать на 2 спеках, проверить что связки == ДО, и пере-прогнать матчинг. Откат — через встроенный снимок истории + бэкап БД.
