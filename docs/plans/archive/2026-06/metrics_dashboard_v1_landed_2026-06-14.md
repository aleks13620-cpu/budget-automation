### Что закрыто
1. **Ветка.** Переведено на `feat/metrics-dashboard-v1`, базируется на `origin/main = c00c3a2`. `git diff origin/main..HEAD` пустой (не коммитили).
2. **Top-1 SQL.** В `metricsDashboard.ts` `ORDER BY m2.is_selected DESC, m2.confidence DESC, m2.id ASC` (брифа §2.2). Теперь зеркалит логику матчера (`matching.ts:486-494` и `tierBreakdown` в `matching.ts:741-747`).
3. **Все типы матчей в ответе.** Интерфейс `ProjectMetrics` расширен полями `manual_top1`, `exact_article_top1`, `name_characteristics_top1`. В сноску `MainMetrics.tsx` выведены все 7 типов + подтверждено оператором + без варианта, с фильтром «показывать только > 0». Контроль-предикат «сумма top-1 типов + без варианта = `spec_total`» считается на фронте, при расхождении пишет `console.warn` (не падает).

### Контроль-замер top-1 расхождений (главный гейт §3 п.3)
Скрипт `backend/scripts/dashboard_top1_check_2026-06-14.ts` — берёт у прода `/api/projects/:id/matching` для пр.6/11/12/13, считает top-1 двумя пикерами в JS (NEW SQL = `isSelected DESC → conf DESC → id ASC`, OLD SQL = `conf DESC → id ASC`), сравнивает.

**Результат на текущем снимке прода:** на ВСЕХ 4 проектах разница NEW vs OLD = 0. То есть:
- пр.6 Сокольи ВК: 0 расхождений
- пр.11 Ласточка ОВ: 0 расхождений
- пр.12 ЖК у БКК ОВ: 0 расхождений
- пр.13 ЖК БКК ВК: 0 расхождений

**Расхождение с цифрами брифа (17/118/3/2).** Бриф ожидал, что OLD-SQL ошибается на 17/118/3/2 строках. На текущем снимке прода оказалось 0. Диагностика (`dashboard_diagnose_2026-06-14.ts`): для ВСЕХ строк, имеющих матчи, ровно один матч имеет `is_selected=1` И ОН ЖЕ — с максимальной `confidence` среди соперников. Поэтому два пикера дают тот же id.

**Интерпретация.** Семантический фикс правильный (теперь SQL зеркалит логику матчера и не сломается, если матчер выберет НЕ самый уверенный по сложному тай-брейку dnScore→qty→conf), но магнитуда визуального изменения = 0 на этом снимке прода. Цифры брифа (17/118) могли быть замерены до недавнего перематчинга или на другом срезе. Не подгоняю.
