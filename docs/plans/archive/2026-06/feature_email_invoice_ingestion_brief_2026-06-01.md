# Фича: приём счетов от поставщиков по e-mail (inbound ingestion)

**Дата:** 2026-06-01
**Статус:** ПРЕДВАРИТЕЛЬНЫЙ ЧЕРНОВИК (pre-clarification). НЕ в активном плане. Код не начат.
**Зависит от:** ответов заказчика (раздел 8) — без них точную архитектуру финализировать нельзя.

---

## 1. TL;DR

Идея давно зафиксирована в продуктовых документах как **«НЕ реализовано», сознательно отложено до ~10 активных клиентов**
(`.business/products/product-1.md`, `architecture/05-интеграции/README.md`, `idea/04-research/what-to-avoid.md`).
Этот документ — заготовка на момент, когда мы выйдем на точку сборки: что строить, в каком порядке,
и что **сначала спросить у заказчика**, чтобы не строить архитектуру вслепую.

Технически парсинг — НЕ узкое место (он уже есть и переиспользуется). Узкое место — **маршрутизация
«письмо → в какой проект»** и **инфраструктура почтового ящика на серверах РФ**.

## 3. Центральная архитектурная проблема: «письмо → какой проект?»

Существующий пайплайн **строго проектно-ориентирован**: счёт всегда грузится в конкретный `projectId`.
Письмо приходит в ящик **без контекста проекта**. Это главный вопрос; всё остальное — механика.

| # | Вариант маршрутизации | Плюс | Минус | Когда уместен |
|---|---|---|---|---|
| A | **Алиас на проект** (`invoices+proj42@domain.ru`, plus-addressing) — снабженец шлёт на адрес проекта | Полный авто-роутинг, тема/отправитель не важны | Меняет поведение снабжения (надо слать на новый адрес) | Когда заказчик готов изменить процесс рассылки |
| B | **Токен в теме/теле** (`[P42]` в теме RFQ, поставщик сохраняет тему в ответе) | Работает в reply-цепочках | Хрупко: поставщики меняют тему, начинают новый тред | Доп. сигнал, не основной |
| C | **Отправитель → поставщик → проект** | Авто-идентификация поставщика | Один поставщик в N проектах → по отправителю проект НЕ определить | Только как часть, не самостоятельно |
| D | **Триаж-ящик «Входящие»** — всё падает в общий лоток, система парсит и определяет поставщика, **оператор раскидывает по проектам** | Не меняет поведение 20 поставщиков; человек в петле = безопасно | +1 шаг оператору | **Прагматичный MVP** |

**Рекомендация:** старт с **D (триаж-ящик)** как безопасного дефолта + **A (алиас)** как ускоритель для
однозначных случаев на Phase 3. Но финал — за ответом заказчика (вопросы 1–3).

## 4. Предлагаемая архитектура (эскиз, minimal, под solo-dev / 1 контейнер)

```
   [RU mailbox: Yandex360 / Mail.ru biz / self-host на VPS]
                     │  IMAP (unseen)
                     ▼
   services/inbox/poller.ts         ← setInterval или node-cron В ТОМ ЖЕ процессе Express
     · fetch писем (imapflow)         (для 1–3 юзеров отдельный воркер не нужен)
     · parse вложений (mailparser)
     · фильтр расширений = текущий allowlist (.pdf/.xlsx/.xls/изобр.), cap 50MB
     · сохранить в UPLOAD_DIR (тот же том)
                     │
                     ▼
   inbound_emails / inbound_attachments  ← НОВЫЕ таблицы; dedup по message_id + sha256
                     │
                     ▼
   services/inbox/supplierResolver.ts   ← from-addr → suppliers.email (СПЯЩЕЕ поле!) →
     · точное совпадение по email          supplier_id; fallback fuzzy по имени; иначе null
                     │
            ┌────────┴─────────┐
            ▼ (A/B: проект определён)   ▼ (D: проект неизвестен)
   авто-assign project_id          триаж-лоток «Входящие», status=pending
            │                            │  оператор жмёт «В проект →»
            └────────────┬───────────────┘
                         ▼
   processInvoiceFile(file, projectId, db)   ← СУЩЕСТВУЮЩАЯ функция, 0 нового парсинга:
                         │                      НДС/скидки/per-supplier конфиг/GigaChat — как в UI
                         ▼
                invoices / invoice_items (как сейчас)
```

**Новые компоненты (всё аддитивно, ничего существующего не ломаем):**
1. `services/inbox/poller.ts` — IMAP-поллинг (или IDLE), извлечение вложений, дедуп.
2. `services/inbox/supplierResolver.ts` — отправитель → поставщик (наконец задействует `suppliers.email`).
3. `routes/inbox.ts` — API триаж-лотка: список входящих, «в проект», «отклонить», «дубликат».
4. Frontend `InboxPage` — лоток входящих; результат парса показываем существующим `InvoicePreview`.
5. Новые таблицы `inbound_emails`, `inbound_attachments` (через `CREATE TABLE IF NOT EXISTS`, как весь проект).
6. `.env`: IMAP host/user/pass/folder, интервал поллинга, feature-flag (по умолчанию ВЫКЛ).

**Дедуп** переиспользует идею `gigachatFileCache` (SHA256 файла): один счёт, присланный дважды / в reply-цепочке, не задваивается.

## 5. Ограничения проекта, которые жёстко влияют на дизайн

- **Данные на серверах РФ** (ключевой констрейнт из `project_overview`): ящик ОБЯЗАН быть на российском
  провайдере (Yandex 360 / Mail.ru для бизнеса / self-host на VPS). **Не Gmail / не O365.**
- **Новая поверхность атаки** на приложении без auth: вредоносные вложения, zip-бомбы, спуфинг отправителя,
  переразмер. Митигации: текущий allowlist расширений + cap 50MB, sha256-дедуп, sender-allowlist (опц.),
  парсер только читает (не исполняет). Для MVP **триаж с человеком в петле** снимает риск авто-доверия письму.
- **Один контейнер / один VPS, синхронный better-sqlite3**: поллер делаем in-process (setInterval/node-cron),
  не блокируя event-loop долгими операциями; отдельный воркер — оверкилл для 1–3 юзеров.
- **Нет миграций**: новые таблицы — через `CREATE TABLE IF NOT EXISTS` в `schema.ts`.

## 6. Поэтапный план (каждая фаза самостоятельно деплоится; ложится на 5-move ритм)

| Фаза | Что | Результат / проверка | Гейт |
|---|---|---|---|
| **0. Решение** | Ответы заказчика (разд. 8), выбор модели маршрутизации + провайдера ящика | Зафиксированы решения | ← блокирующий гейт, кода нет |
| **1. Read-only ingest** | IMAP-поллинг → вложения в `UPLOAD_DIR` → `inbound_*` таблицы → дедуп. Парсинга НЕТ. Feature-flag OFF по умолчанию | Письма появляются строками в БД; дубликаты не плодятся | Не трогает прод-путь UI |
| **2. Resolver + триаж UI + ручной assign → `processInvoiceFile`** | Отправитель→поставщик; оператор раскидывает по проектам; существующий пайплайн парсит | Базовая ценность с человеком-гейтом; задействован `suppliers.email` | Интеграционный тест на боевой путь |
| **3. Авто-роутинг** | Алиас/токен (A/B) для однозначных писем; триаж — для остальных | Часть писем сама попадает в проект | Гейт авто-доверия письму |
| **4. Харднинг** | Sender-allowlist, ретраи/ошибки, уведомления «N новых счетов», наблюдаемость, reply-треды | Прод-готовность | pre-deploy-check PASS |

## 7. Что нужно для реализации (информация / доступы / инфра)

- **Выделенный почтовый ящик** на RU-провайдере + учётные данные (IMAP host/login/app-password/папка).
- **Решение по модели маршрутизации** (разд. 3) — главный вход.
- **Реальные образцы писем** от поставщиков: форматы тем, паттерны вложений, мульти-вложения, reply-цепочки,
  «счёт + спека отдельными файлами». У заказчика эти письма уже есть — нужны 20–50 примеров.
- **Нужна ли исходящая авто-рассылка RFQ** сейчас или потом (тогда + SMTP) — влияет на объём.
- **Оценка объёма** (писем/день) — выбор интервала поллинга / IDLE.
- **Хостинг-решение**: поллер в текущем контейнере vs отдельный сервис (рекомендую in-process).

## 8. Вопросы заказчику (готовый список — задать ДО финализации архитектуры)

> 🔴 — блокирующие (без ответа нельзя начинать). 🟡 — влияют на детали.

**Маршрутизация (как письмо находит проект):**
1. 🔴 Готовы ли вы, чтобы снабжение слало счета на **выделенный адрес проекта** (напр. `proj42@…`), или удобнее
   единый ящик и **раскидывать счета по проектам вручную** в интерфейсе? *(выбор A vs D — определяет всю архитектуру)*
2. 🟡 В ваших RFQ-письмах есть устойчивый **код проекта в теме**? Поставщики отвечают «в тему» или новым письмом?
3. 🟡 Бывает, что **один поставщик** одновременно в **нескольких ваших проектах**? (если да — отправителя для выбора проекта недостаточно)

**Почтовый ящик / инфраструктура:**
4. 🔴 Какой **почтовый провайдер** используете (Yandex / Mail.ru / свой)? Данные обязаны оставаться в РФ — Gmail/Outlook не подойдут.
5. 🔴 Можно ли завести **отдельный технический ящик** только под систему (чтобы не лезть в личную почту снабженца)?
6. 🟡 Это **общий ящик отдела снабжения** или личные ящики? Сколько людей шлёт/получает?

**Идентификация поставщика и контента:**
7. 🟡 Поставщик всегда пишет с **одного и того же адреса**, или с разных (бухгалтерия/менеджер/no-reply)?
8. 🟡 Что в письме, кроме счёта: спецификации, КП, прайсы, картинки-подписи? Нам нужно **отличать счёт** от прочего.
9. 🟡 Один счёт = одно письмо, или присылают **несколько счетов в одном письме** / архивом (zip/rar)?

**Объём и крайние случаи:**
10. 🟡 Сколько писем со счетами в день/неделю в пик? (интервал опроса)
11. 🟡 Бывают **дубликаты** (тот же счёт повторно, «исправленный счёт», reply с правкой)? Как вы сейчас понимаете, какой актуальный?
12. 🟡 Что делать с **нераспознанным** письмом (не от поставщика / не счёт) — игнор, в лоток «разобрать», уведомление?

**Процесс и UX:**
13. 🟡 Нужны ли **уведомления** «пришло N новых счетов» и куда (в интерфейс / на почту / Telegram)?
14. 🟡 Кто будет **подтверждать** привязку счёта к проекту — тот же оператор-сметчик?
15. 🟡 Насколько критичен **порядок секунд/минут** (realtime) или достаточно опроса раз в N минут?

**Исходящая рассылка (смежная фича):**
16. 🟡 Нужна ли в этой итерации **авто-рассылка запросов** поставщикам (RFQ), или только **приём** ответов?
    *(приём и отправка — разный объём; в продуктовых доках оба помечены «не реализовано»)*

## 9. Открытые техрешения на нашей стороне (решаем сами после ответов)

- IMAP-библиотека: `imapflow` + `mailparser` (поддерживаются, активные) vs провайдерский API (Yandex 360 / Mail.ru).
- Поллинг: `setInterval` (минимализм) vs `node-cron` (расписание) vs IMAP IDLE (near-realtime).
- Где хранить маппинг «алиас/код → проект»: поле в `projects` или отдельная таблица.
- Заполнение `suppliers.email`: задним числом из истории счетов + при ручном assign в триаже.
