## 0. Как этим управлять (оркестратор + воркер-чаты)

- **Один чат-оркестратор** (этот) держит процесс, контекст и сверку со стратегией; **сам код НЕ пишет**.
- **Каждая код-фаза = отдельный воркер-ЧАТ** (новое окно Claude Code в этой же папке), НЕ субагент в окне оркестратора — чтобы реализация не жгла контекст оркестратора. Механика:
  1. Оркестратор кладёт **самодостаточный бриф-файл** `docs/plans/active/worker_brief_*.md` (воркер не помнит обсуждений — в брифе ВСЁ: цель, шаги, файлы, гейт «Готово», ограничения, регресс-тривайр §6).
  2. Владелец открывает новый чат → «выполни `docs/plans/active/worker_brief_*.md`». Воркер работает **в отдельной ветке, НЕ пушит, НЕ деплоит**.
  3. Воркер пишет краткий **РЕЗУЛЬТАТ** (ветка, изменённые файлы, тесты) в `*_result.md`. Оркестратор читает только это + **диф**, не транскрипт.
- **Параллельные воркер-чаты — ТОЛЬКО если брифы трогают РАЗНЫЕ файлы / независимы.** Код-связанные (один зависит от правок другого) — **серийно** (`reflection_2026-05-31`).
- **Ёмкость фазы ≤ 4 ч.** Воркер видит превышение — СТОП, возврат оркестратору на дробление.
- **Гейт оркестратора после КАЖДОЙ код-фазы — МЕДЛЕННО, по одной (владелец продавил 2026-06-05):** на ветке воркера — `npm run build` (backend+frontend) + **5-move `pre-deploy-check` skill → PASS** (проверка «Готово» как **diff/факт, не рассказ**) + регресс-тривайр §6 не упал. Только PASS → commit именованных файлов (ASCII-сообщение) → push → деплой → **прод-верификация** (push ≠ deployed). Любой FIX → назад воркеру, НЕ пушим.
- **Блоки B–G вооружаются ТОЛЬКО после GATE-A.** До него продуктовый код не коммитим.

## 2. Карта фаз и порядок

```
A (разведка) ──► GATE-A ──► B (распознавание)
                      ├────► C (признаки) ──► D (независимость, в «тень»)

                      ├────► F (чистка, после B)
                      └────► G (малые победы / доверие оператора, К4)
```
**Жёсткое правило:** C (признаки) → потом D (независимость), **никогда наоборот**. Снятие фильтра поставщика на голой лексике = тупик.

# ПЛАН «North-Star» — измеримый рост качества на ТЕКУЩИХ данных (утверждён владельцем 2026-06-08)

> Контекст: каталог-перенос ПОДТВЕРЖДЁН (46.4% durable на held-out Сокольих, см. reflection_2026-06-08). Дальше — НЕ гнать сыроватое оператору, а измеримо растить качество, выжимая ТЕКУЩИЕ данные по максимуму, без оператора. Прогоны = воркер-субагенты в отдельных чатах (модель эскалируется при нужде); оркестратор гейтит честность + держит контекст чистым; память ведёт оркестратор.

## North-Star метрика (должна РАСТИ)
**Верность матчинга@1 — доля строк, сопоставленных ВЕРНО самой системой против ЭТАЛОНА.** НЕ «покрытие/сматчено» (снято как фальшивое — K3). Две проекции:
- **AI-ON верность@1** — операторская (что видит оператор; ИИ = один из инструментов, оператору неважно как достигнуто).
- **durable@1 (AI-OFF + каталог)** — стратегический капитал (растёт → ИИ-зависимость и расходы падают).
Ведущие индикаторы конвейера: распознавание входной спеки (% чистых строк) → распознавание счетов → матчинг@1. Эталон: Сокольи по цене + исторические вход→выход.
**ВАУ-планка (из бизнес-обещания «80% авто + 15 мин», project_overview):** AI-ON@1 **≥80% = ВАУ**; 60–80% = рабочее, не ВАУ; **<60% = kill-зона** (корневой разбор).

## Фазы
- **A — настоящий baseline.** Multi-project held-out бенчмарк (Сокольи + Ласточка + train/test split на Самара/Совжи/Престиж), режимы AI-ON и durable, на ПОЛНЫХ наборах (не 28 трудных). = North-Star baseline + переиспользуемый движок-метрика.
- **B — рычаги текущих данных + дельта «до/после»:** C2 (синоним клапан/кран), полная загрузка истории по инвентарю, C1 (ре-нормализация alias_norm). [A+B в одном брифе `worker_brief_verity_benchmark_baseline.md` — ЗАПУЩЕН 2026-06-08.]

- **D — дашборд:** тонкая обёртка над метрикой A (для владельца, ВНЕ зоны оператора); операторский «машина сама X% + тренд» — на показе. Бриф пишется ПОСЛЕ того, как A даст метрику (UI на пустой метрике не строим).

## 6. Точка отсчёта распознавания (К3, владелец ПРИНЯЛ 2026-06-05)
Раньше всё мерили одним «333/268/44». По коду это **разовый снимок ПОКРЫТИЯ одного проекта**: 333 сматчено / 268 подтверждено / 44 не сматчено ([matching.ts:1767-1788](../../../backend/src/routes/matching.ts)). Это **не верность** и **не межпроектная стабильность**. Разделяем ДВЕ вещи:

1. **Регресс-тривайр «не сломал ли работающее»** (безопасность, в каждой код-фазе; НЕ метрика качества). Считать **свежим, read-only** из боевой БД по ВСЕМ активным проектам ([matching.ts:1768-1788](../../../backend/src/routes/matching.ts)), разбивка **по поставщику и тиру** ([metricSnapshots.ts:44-52](../../../backend/src/services/metricSnapshots.ts)). Правило: после правки число **подтверждённых** не должно УПАСТЬ (рост — ок); падение тира `learned_rule` ловит порчу обучения. Берётся в начале фазы, не замороженный снимок 05-29.
2. **Метрика ВЕРНОСТИ «правильно ли матчим»** (качество). В коде её НЕТ — метрики/training меряют только **покрытие** ([schema.ts:249](../../../backend/src/database/schema.ts), [metricSnapshots.ts:26-39](../../../backend/src/services/metricSnapshots.ts), [matching.ts:2008-2014](../../../backend/src/routes/matching.ts)); подтверждение оператором ≠ доказательство верности. «Правильная точка» = доля ВЕРНЫХ против **эталона**, а эталон есть из исторических проектов (К4) → строится в E2 **без ожидания заказчика**.

**Итог:** «333/268/44» снят с роли эталона. Безопасность = свежий per-supplier/per-tier счёт подтверждённых; качество = верность против исторических эталонов.
