## Контекст (главное)
Парсер спеки PDF якорит родителя ТОЛЬКО по `position_number` (`backend/src/services/gigachatSpecFromPdf.ts:linkPdfParentChildren:188-194`). У реальных заказчиков (Ласточка, Сокольи горы) дочерние строки **не имеют номера ПО ДИЗАЙНУ документа** (один номер на семью радиаторов, варианты-типоразмеры под ним без нумерации). Подтверждено пробой fitz+pdfplumber: у Ласточки 34 родителя с номером, 95% детей без. Прод-данные Ласточки (проект 11): 328 строк, position_number 0/328, parent_item_id только 10/328. Иерархия **развалена**, в матчинг идёт каша.

`SPECIFICATION_PROMPT` (`gigachatSpecFromPdf.ts:34-108`) уже просит LLM размечать смысл (children с `position:null`), но `mapPdfItemsToRows` (~:333) перемалывает результат LLM ТЕМ ЖЕ якорем по номеру → LLM-разметка иерархии теряется. + Условие LLM-фолбэка (`:454 if pdfplumberFiltered.length > 0 return`) слишком жёсткое — на Ласточке pdfplumber вернул 737 → LLM не вызывается.

## Цель

## Скоуп (точечно, 5 правок в одном поле кода)
1. **Расширить `SPECIFICATION_PROMPT`** (`gigachatSpecFromPdf.ts:34-108`): в JSON-схему ответа добавить опциональные поля для каждой строки: `parent_position` (номер родителя, если он есть в документе) или `parent_name_hint` (короткая подсказка имени родителя). Чётко в инструкции: «для дочерней строки без `position` укажи `parent_position` или `parent_name_hint`».
2. **Новый якорь в `linkPdfParentChildren`** (`gigachatSpecFromPdf.ts:180-280`): ЕСЛИ у item есть `parent_position`/`parent_name_hint` от LLM — использовать ЕГО (искать родителя в уже разобранных rows). FALLBACK на текущую position-логику — когда LLM-полей нет (это сохранит 6/8 успешных case'ов).
3. **Ослабить условие LLM-фолбэка** (`gigachatSpecFromPdf.ts:454`): не просто `length > 0`, а «pdfplumber вернул, НО качество низкое» → всё равно вызвать LLM. Сигнал низкого качества — `noPosFraction > 0.5` (доля строк без номера, считается из `evaluateSpecPdfParseQuality`).
