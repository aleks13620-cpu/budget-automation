# research — проверка идеи «разделение спецификации» (21–23.08.2026)

Разовые скрипты, которыми проверялась гипотеза перед тем, как что-то строить в системе.
Живут здесь, чтобы результат дня не пропал и чтобы прогон можно было повторить.

**На сервере они не исполняются** — Dockerfile папку `price-harvester/` в образ не копирует,
сбор идёт с рабочей машины. Одно исключение: `zapis_v_sistemu.py` — он и есть перенос
результата в систему, порядок ниже.

| Файл | Что делает |
|---|---|
| `klassifikator_pozicij.py` | делит позиции спецификации на 4 группы: марка / словами / по чертежу / по запросу |
| `zamer_sloj_marka.py` | прогон слоя «с заводской маркой»: поиск → карточка → сверка марки → цена. Выдаёт лист для снабженца (см. ниже) |
| `zamer_varianty_bez_marki.py` | по позициям без марки собирает НЕСКОЛЬКО кандидатов и разбирает каждого через ИИ |
| `test_ii_razbor_harakteristik.py` | сверка вердиктов ИИ с ручным эталоном на 10 позициях |

## Выдача для снабженца (24.08)

`zamer_sloj_marka.py` без аргументов делает полный прогон и кладёт три файла в `out/`:

| Файл | Зачем |
|---|---|
| `Арта_цены_по-артикулам.html` | то, что щупает Иван: та же таблица + поиск по позиции/марке/продавцу и переключатель «скрыть тех, кто не отдал цену». Самодостаточная — открывается двойным кликом с диска и по ссылке с прода одинаково, наружу ничего не грузит |
| `Арта_цены_по-артикулам.xlsx` | то же самое для Excel: строка на КАЖДОЕ найденное предложение, внутри позиции по возрастанию цены, ссылка на карточку кликабельная |
| `zamer_layerC_hits.json` | весь прогон целиком, включая все предложения по позиции |
| `zamer_layerC_clean.csv` | плоская сводка для нас (по одному минимуму на позицию) |

Два режима без сети:

- `python zamer_sloj_marka.py selfcheck` — проверяет сборку листа и разбор цены. Гонять после любой правки.
- `python zamer_sloj_marka.py render` — перерисовывает лист и страницу из `zamer_layerC_hits.json`. Вид меняется за секунды, прогон 12 минут повторять не надо.

**Страницу проверять в браузере, а не по коду.** Дюймовая кавычка в названии (`G1/2"`) рвала
атрибут `data-k`, и две строки выпадали из поиска: в таблице они были, а по слову «lunda»
не находились. Скриншот этого не показывает — видно только когда потыкаешь поиск.
В `selfcheck` заведён случай с дюймом.

**Минимальную цену молча не выбираем.** По теплосчётчику (95 шт) самое дешёвое предложение
оказалось страницей серии на сайте производителя — 1 650 ₽ против настоящих 13 499…54 900 ₽.
Тихий выбор минимума врал бы на миллион. Сумма считается в каждой строке, решение за снабженцем.

## Перенос цен на прод — порядок

Экспорт спецификации в системе показывает найденные цены, но берёт их из таблицы
`external_prices` **той базы, где работает**. На проде своя база, и деплой её не трогает.
Значит после выкладки кода колонки будут пустыми, пока не сделано вот это:

1. Загрузить спецификацию на прод как проект — через интерфейс, обычной кнопкой загрузки.
2. Узнать **`specification_id`**, а не номер проекта. Это разные вещи: у одного проекта бывает
   несколько загрузок, каждая со своим `specification_id`, и на проде номер не совпадёт
   с локальным. Взять из таблицы `specifications` прод-базы:
   `select id, file_name, project_id from specifications order by id desc limit 5`.
3. Прописать его в `SPEC_ID` в `zamer_sloj_marka.py` и `zapis_v_sistemu.py`.
4. Прогнать поиск против прод-данных: `python zamer_sloj_marka.py` (12 минут на 54 позиции).
5. Записать результат: `python zapis_v_sistemu.py` с `BUDGET_DB_PATH` на прод-базу.
   **Как до неё добраться.** База лежит на сервере файлом `/root/budget-automation/database/
   budget_automation.db` и смонтирована в контейнер томом; скриптов там нет — Dockerfile папку
   `price-harvester/` не копирует. Значит либо ставить питон-окружение и секреты на сервер
   и запускать по ssh оттуда, либо снять копию базы (workflow «Recover» делает это, не меняя
   сервер), прогнать локально и вернуть файл обратно. Второй путь проще, но пока копия
   гуляет, работать в системе нельзя — правки, сделанные в это время, потеряются.
6. Проверить выгрузкой: открыть экспорт проекта и убедиться, что цены встали в свои строки.

**Строки из локальной базы дампом НЕ переливать.** `spec_item_id` — сквозной счётчик по
всей базе, и те же номера на проде принадлежат совсем другим позициям. Цены молча встанут
в чужие спецификации, а выгрузка при этом отдаст 200 и будет выглядеть нормально. В экспорте
на этот случай стоит сверка ещё и по `project_id`, но полагаться на неё как на разрешение
переливать дампом нельзя — она предохранитель, а не способ.

## Что важно знать при возврате к коду

**Марка ищется по признаку во всех полях позиции**, а не в конкретном поле: разные парсеры
кладут её в `product_code`, в `characteristics`, в `manufacturer`, прямо в `name`.

**Типоразмеры маркой не считаются.** `DN20`, `Ду25`, `Ру40`, `Tmax180`, `G1/2` — по ним поиск
уходит на любой товар того же диаметра. Это проверено: «прямой DN20» находил термостатический
клапан Herz. Отсев этого мусора поднял находимость слоя с 45% до 85%.

**Цена берётся только с карточки товара** (schema.org Product / og:type=product). Больше трёх
товаров в разметке — это витрина, страница отвергается.

**`itemprop="price"` на странице бывает дважды.** У `nevagrad.com` рядом лежат битый
`<meta content="14">` и настоящий `<span content="14573.95">`. Раньше брали первый попавшийся —
получали «преобразователь давления за 14 ₽». Берём наибольшее: обрезанный префикс тысяч всегда
меньше настоящей цены. Проверено на трёх карточках: 14 → 14 573,95; 5 → 5 099,10; 124 → 124 281,65.

**Сверка марки фильтрует не везде.** Из 54 позиций слоя у 15 «марка» — типоразмер радиатора
(`C22-400-600`), у 4 — степень защиты `IP54`. Там сверка не отсекает соседние типоразмеры одной
серии: у `VFG-2` и `MNF-R2` разброс предложений доходит до 23–31 раз именно поэтому, а не из-за
разницы продавцов. Итоговую сумму по слою как факт называть нельзя.
